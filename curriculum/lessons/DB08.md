# DB08｜事务、隔离与故障恢复

先修：DB06。先修待验证时先做前节验收；通过可跳过重复讲解。

## 学完要能做到

## 讲解与例题


### 1. 事务边界对应一个业务动作

从账户1向账户2转20，需要扣款和入账一起完成。事务把它们作为一个整体提交或回滚：

```sql
CREATE TEMP TABLE accounts(id INTEGER PRIMARY KEY,balance INTEGER NOT NULL CHECK(balance>=0));
INSERT INTO accounts VALUES(1,100),(2,100);
BEGIN;
UPDATE accounts SET balance=balance-20 WHERE id=1;
UPDATE accounts SET balance=balance+20 WHERE id=2;
ROLLBACK;
SELECT * FROM accounts ORDER BY id;
```

回滚后都是100；重新运行事务并COMMIT后为80、120。需要同时验证收款账户存在，否则UPDATE可能影响0行却不报错，ACID不会自动理解“必须成功入账”的业务规则。

### 2. ACID逐一对应问题

Atomicity原子性：整体提交或撤销。Consistency一致性：事务配合约束与业务逻辑维护规定的不变量。Isolation隔离性：并发事务之间允许看到什么。Durability持久性：提交后的数据按系统配置提供持久保证。

隔离不是“只有一个事务能执行”。例如Read Committed通常每条语句取新的已提交快照，所以同一事务两次查询可能看到不同已提交值。PostgreSQL默认Read Committed不允许脏读；Repeatable Read使用事务快照，但不能把它理解成排除了所有业务并发异常。

### 3. 双会话观察，不只背名词

使用seed.sql所在的空练习库。A执行 `BEGIN ISOLATION LEVEL READ COMMITTED; SELECT amount FROM orders WHERE id=103;`。B把103金额更新为75并提交。A再SELECT会看到75，然后ROLLBACK。把103重置50并提交，再用Repeatable Read重复：A第一次SELECT建立快照后，B提交75，A仍看到50。最后A回滚、B重置50。

### 4. 崩溃与日志

提交不要求所有修改的数据页已经写回最终位置。以WAL为例，先保证相应日志按规则持久化，再依靠恢复机制重放必要修改。课堂中的undo/redo模型要区分具体数据库实现；本节不把通用恢复算法等同于PostgreSQL的全部内部细节。

“请求超时”不等于“数据库未提交”。客户端重试还要考虑是否造成重复业务动作，这会衔接后续幂等设计。
