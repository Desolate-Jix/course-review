# DB07｜索引、执行计划与性能验证

先修：DB06。先修待验证时先做前节验收；通过可跳过重复讲解。

## 学完要能做到

用真实执行计划定位问题，区分估计成本与实际耗时；索引前后结果一致，并解释一个不走索引的合理场景。

## 讲解与例题


### 1. 从扫描成本理解索引

没有适合的索引时，数据库可能扫描表中所有页并检查条件。索引保存检索结构，帮助定位候选记录。B+树的多层节点缩小搜索范围，叶层有序排列有利于范围查询。索引自身占空间，插入、删除和相关字段更新也需维护它。

索引不是“有就快”。小表、返回大部分记录、频繁随机访问数据页等情况下，顺序扫描可能合理。联合索引还要考虑列顺序、过滤和排序方式；本阶段先实验单列，联合索引作为后续扩展。

### 2. 读计划要区分估计与实际

EXPLAIN显示计划和估计成本；cost不是毫秒。EXPLAIN ANALYZE真的执行语句，并给出实际行数、时间等。讲义只用SELECT，避免把有副作用的语句当成只读检查。

```sql
CREATE TEMP TABLE lab_orders AS
SELECT g AS id,g % 1000 AS user_id,g AS amount
FROM generate_series(1,100000) AS g;
ANALYZE lab_orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_orders WHERE user_id=42;
CREATE INDEX lab_orders_user_idx ON lab_orders(user_id);
ANALYZE lab_orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_orders WHERE user_id=42;
```

结果应均为100行。计划可能从Seq Scan变成Bitmap或Index扫描，但不预设具体节点和加速倍数。若没改变，保存真实结果并检查选择率、数据规模和统计信息。

### 3. 控制比较条件

同一查询、数据与结果集合，分别记录有／无索引。连续运行会受到缓存和系统负载影响，因此记录首次和后续结果，不把一次时间差当作普遍规律。再把条件放宽为 `user_id < 900`，观察90%记录被选中时的取舍。
