# API｜后端API、FastAPI与安全

阶段：C｜后端/全栈专项。先修：NET、DB08、PYX、ENG。

从单服务正确性开始，再进入缓存和分布式。认证、授权和数据验证都必须在服务端落实。

本页为可直接复习的题目、答案要点与追问边界；首次遇到概念，先读资料并完成例子。它不等同于已编写完整教科书讲义，也不代表已经掌握。题量随覆盖缺口增长，不设上限。

|题号|问题|参考答案要点|追问与边界|
|---|---|---|---|
|API-01|REST资源设计与API契约是什么？|用资源、方法、状态码表达操作，明确请求响应字段、错误格式、版本和兼容策略；不等于URL看起来像名词就设计完成。|修改字段名称能直接发布吗？需考虑旧客户端与迁移期兼容。|
|API-02|认证与授权有什么区别？|认证确认身份，授权判断该身份对具体资源和操作是否被允许；登录成功不意味着可读取任意用户数据。|改请求中的user_id就能看别人数据怎么办？服务端按当前身份校验对象级权限。|
|API-03|密码与令牌怎样存储和验证？|密码使用适合密码的带盐慢哈希，令牌需校验签名、有效期与受众等；避免日志泄漏，按威胁模型管理存放和撤销。|Base64或普通快速哈希够吗？编码不保密，快速哈希不适合作为独立密码保护方案。|
|API-04|SQL注入与参数化查询如何联系？|将数据参数与SQL结构分离，避免字符串拼接让输入改变语句含义；动态表名排序列需白名单等结构控制。|ORM就绝对无注入吗？不是，原始SQL和不安全动态拼接仍可能有风险。|
|API-05|输入验证、业务验证与数据库约束怎样配合？|输入层检查类型形状，业务层检查规则与权限，数据库层维护最终唯一性和引用约束；各层处理不同失败。|前端已经验证能省服务端吗？不能，客户端可绕过且并发状态会变化。|
|API-06|请求超时、重试、幂等键怎样设计？|超时表示结果可能未知；重试只对合适错误、有界退避并使用业务幂等保护；同键同请求应得到一致业务结果。|仅把键放缓存后再写库安全吗？存在崩溃窗口，应设计原子状态/唯一约束及结果恢复。|
|API-07|连接池与事务范围有什么关系？|池复用连接但数量受数据库承载限制；事务应短且明确归还/回滚，避免在事务中长时间等待外部网络。|池越大越快吗？不，过多连接可增加争用与排队，需测吞吐延迟。|
|API-08|ORM的N+1查询是什么？|先查N个对象，再为每个对象单独查关联，产生额外N次往返；批量加载或适当连接可改善。|所有关联一次JOIN回来一定好吗？可能行数膨胀，需结合结果粒度和分页。|
|API-09|FastAPI的def与async def怎样选择？|async适合可await的调用；框架处理同步路由/依赖时可在线程池运行；直接从async函数调用同步阻塞函数不会自动变异步。|CPU重活放async端点会怎样？阻塞事件循环，应考虑任务隔离与容量设计。|
|API-10|依赖注入与请求生命周期有什么用？|将数据库会话、鉴权等依赖由框架组织，便于复用、测试替换与清理；资源生命周期需与使用范围一致。|依赖注入等于全局单例吗？不是，作用域和缓存规则需明确。|
|API-11|文件上传、后台任务和分页有什么边界？|限制大小与类型、校验权限、隔离文件路径；后台任务需考虑进程退出后的丢失；分页要稳定顺序与上限。|内存后台任务等于可靠消息队列吗？不是，持久化与重试需额外机制。|
|API-12|如何设计错误响应与限流？|统一可操作错误码和请求ID，区分客户端/服务端问题，不暴露敏感内部信息；限流需定义身份、窗口、额度及拒绝行为。|只在前端禁按钮能防滥用吗？不能，服务端必须实施策略。|

## 课堂验证

用课堂API模拟重复创建请求、非法输入、跨用户资源访问和提交成功但响应丢失；验证幂等键与数据库唯一约束的处理。

**预期与判分：** 重复请求最多产生一条业务记录；相同键不同载荷应冲突而非静默复用；越权请求被拒绝；超时后可查询结果。允许先写请求与状态时间线再编码。

**英文关键词：** authentication, authorization, idempotency key, connection pool, dependency injection。用“结论→机制→本例→边界”组织短答。
