# REACT｜React与Next.js

阶段：C｜前端/全栈专项。先修：JS、WEB；熟悉组件与基本状态。

结合现有前端经历学习，但不能把课堂方案写成已完成的项目工作。框架缓存默认值等按项目锁定版本核实。

本页为可直接复习的题目、答案要点与追问边界；首次遇到概念，先读资料并完成例子。它不等同于已编写完整教科书讲义，也不代表已经掌握。题量随覆盖缺口增长，不设上限。

|题号|问题|参考答案要点|追问与边界|
|---|---|---|---|
|REACT-01|props与state有什么区别？|props由外部传入，state是组件维护的渲染状态；都应在渲染中按只读快照理解，变化通过相应更新流程。|直接改数组再set原引用有什么风险？可能无法按预期触发更新且破坏之前快照。|
|REACT-02|为什么setState后马上读还是旧值？|当前处理函数读取本次渲染的状态快照，更新会安排后续渲染；需要基于前值累计时使用函数式更新。|连续两次setCount(count+1)总会加2吗？同一快照下通常不是，函数式更新才表达两次累计。|
|REACT-03|render、commit、协调与key如何联系？|render计算下一UI，commit应用变化；key帮助同级元素跨渲染识别身份和状态保留。|列表用下标作key什么时候风险大？插删排序会让状态错配，应优先稳定业务ID。|
|REACT-04|Hooks为什么不能随便放条件里？|常规状态Hooks依赖稳定调用结构关联状态；应遵循具体Hook规则和lint，而非随意改变调用顺序。|所有名字以use开头API都完全同规则吗？具体API可能有例外，按官方说明核对，不能泛化。|
|REACT-05|useEffect应处理什么？|用于组件与外部系统同步，如订阅、连接和必要的副作用；可在渲染计算的派生值不应无故放Effect。|事件引起的提交都放Effect好吗？通常直接在事件处理更清晰，避免重复执行。|
|REACT-06|依赖数组、闭包过期与清理如何联系？|Effect捕获本次渲染值，依赖用于重新同步；清理上次订阅/任务后再建立新同步，避免旧逻辑继续影响。|空数组就是永远只执行一次吗？不应这样承诺，开发StrictMode可额外做设置清理检查。|
|REACT-07|请求竞态怎样防止旧结果覆盖新输入？|使用取消信号或请求序号/忽略标志，只接受当前请求结果，处理加载、空、错误与取消状态。|取消请求是否保证服务器没执行？不保证，后端写操作仍需幂等保护。|
|REACT-08|useMemo、useCallback、memo怎样取舍？|用于有依据的计算或引用稳定优化；需考虑比较成本、依赖与框架/编译器行为，不作为程序正确性基础。|全部加上一定更快吗？不，先定位瓶颈，再看测量变化。|
|REACT-09|useRef与state有什么区别？|ref保存跨渲染可变值或DOM引用，修改不直接触发渲染；影响显示的数据通常需state。|把所有数据放ref能减少渲染吗？会使界面与数据失同步，不能只追求少渲染。|
|REACT-10|受控表单、状态提升、Context怎么选？|受控表单由状态驱动值；共享状态提升到共同祖先；Context用于跨层传递，需考虑更新范围。|Context等于完整全局状态管理吗？不，缓存、异步数据和订阅粒度可能需要其他方案。|
|REACT-11|CSR、SSR、SSG与hydration如何区别？|CSR主要在客户端生成UI；SSR按请求生成初始输出；SSG在构建或预生成阶段产出；hydration把交互附加到已有HTML。|服务端客户端初始输出不同会怎样？可能产生水合不匹配，应定位时间、随机值与浏览器专属状态。|
|REACT-12|Next服务端组件与客户端组件怎样划边界？|服务端组件适合服务端数据与减少客户端JS；交互、浏览器API及相应Hooks需客户端边界；传递数据遵循框架序列化约束。|客户端组件是否只在浏览器渲染？不应这样理解，初次页面仍可能有服务端预渲染。|
|REACT-13|Suspense、错误边界和路由加载态分别负责什么？|Suspense处理支持其协议的挂起状态，错误边界处理相应渲染错误，路由加载与错误UI按框架规则组织。|错误边界会抓所有异步回调错误吗？不会，事件和异步任务需对应处理。|
|REACT-14|服务端缓存与重新验证怎样回答？|先说明Next/React版本、路由模式和具体缓存层，再说明键、生命周期及失效触发；不能背跨版本默认值。|用户A数据能缓存给B吗？必须隔离身份和权限上下文，敏感响应不能误共享。|

## 课堂验证

写搜索组件：输入A后立即输入B，模拟A较晚返回，保证最终只显示B结果；再测试列表重排后输入状态保持正确，解释key与清理。

**预期与判分：** 竞态测试必须控制响应顺序；展示loading/empty/error；不把开发重复Effect误报为生产双提交。只在有测量证据时宣称性能改善。

**英文关键词：** state snapshot, reconciliation, effect cleanup, stale closure, hydration。用“结论→机制→本例→边界”组织短答。
